## Problem Statement

The owner asked for the app to look like their mockups (`design/mockups/*.svg`):
a pixel-art window with a white and blue notched frame, a dark blue gradient
panel, three hearts, a yellow triforce for the active tab and the row cursor,
yellow arrows around the selected value and for scrolling, and SNES-style
button sprites in the footer (a white d-pad, yellow A/B/X/Y squares, a red
START pill). Step 8 put the mockups' zones, fonts and sizes into
`themes/alttp`, but with `image = none`, a solid `#0c0c34` screen, a drawn tab
separator, and text markers standing in for every sprite. Captured beside the
mockups by `make theme-compare` (step 10), every screen scores around 8 % mean
difference, and the side-by-side images show why: no frame, no gradient, no
hearts, a `>` where a triforce should be, `A` where a yellow button should be.

Nothing in the theme folder is yet produced from the mockups, so there is no
way to rebuild the art if a mockup changes, and no measure of "how close" a
capture is beyond one global score that mixes text rasterisation with layout
errors.

## Solution

`themes/alttp/` gains `frame.png` (the full 640×480 background) and thirteen
sprite PNGs, all produced by a committed generator that renders the mockups'
own vector shapes in the pinned headless Chromium and writes the pixels with
a deterministic PNG encoder. `theme.ini` switches from text markers to those
sprites and from a solid screen to `frame.png`. Then the theme is tuned in
passes with `make theme-compare`, which now also measures, per mockup, how
many pixels differ outside the text and how far each text is from its mockup
position, until every capture matches its mockup's layout or each remaining
difference has a recorded reason.

The owner gets nine side-by-side images (mockup | app | diff) in
`tests/rando/build/theme-compare/`, listed in `notes/owner-todo.md`, to judge
the result. The page size (12), the wrap width (48) and the help line length
(58) stay what step 8 fixed, so steps 9 and 11 still hold.

No code under `app/` changes: the look is theme data, as the plan's goal
requires.

### The generator (new, outside the net)

- A committed table (one line per PNG, tab-separated, in the style of
  `mockup_states.txt`): output file, source mockup, clip box x y w h, scale,
  and the CSS selectors of the elements kept. `frame.png`'s line is marked
  as checked in every mockup.
- A Node script (Playwright, as `mockup_render.js`) that, for each line, opens
  the mockup as `file://` in headless Chromium, refuses any non-`file:`
  request, waits for the Press Start 2P face to be loaded (refused
  otherwise), requires each selector to match exactly one element (one line
  naming the mockup and the selector otherwise), removes every element of the
  root `svg` that is neither in `defs` nor a kept element (or its ancestor),
  sets the root's `viewBox` to the clip box and its size to the box times the
  scale, and screenshots the viewport with a transparent background. For
  `frame.png` it also requires the kept elements' markup to be identical in
  all nine mockups. Sprites have no background rect, so their outside is
  transparent.
- A Python normaliser (`python3 -I`, standard library) that decodes each
  screenshot and writes the PNG the theme ships:
  - size must be the clip box times the scale, rounded;
  - `frame.png` must be fully opaque and is written as colour type 2 (RGB);
  - a sprite must have every alpha 0 or 255 and at least one opaque pixel
    (refused otherwise: a half-transparent edge would blend differently over
    the gradient, the bands and the footer), and is written as colour type 6
    (RGBA) with every transparent pixel stored as `0,0,0,0`;
  - the encoder writes IHDR, one IDAT and IEND only, filter 0 on every row,
    `zlib` level 9: the bytes depend only on the pixels and the host's zlib.
- The RGBA decoding is shared with `theme_compare.py`: its PNG decoder is
  split into a pixel decoder returning RGBA rows and the existing opaque-RGB
  check on top, with no behaviour change (its self-test stays as it is and
  must pass). The normaliser imports it from its own directory explicitly
  (`python3 -I` drops the script's directory from the path), rather than
  holding a second copy of the decoder.
- A driver script, POSIX sh, sourcing `mockup_common.sh`'s `browser_setup`
  (the same `setup:` lines as `make mockups`), with two modes:
  - **check** (`make theme-art`): renders into
    `tests/rando/build/theme-art/`, then compares the decoded pixels (not the
    bytes, so another host's zlib is not a mismatch) of each PNG with the
    committed one in `themes/alttp/`; one `DIFFERENT <file>`, `MISSING
    <file>` or `EXTRA <file>` line per mismatch (EXTRA: a PNG in
    `themes/alttp/` that no table line produces), exit 1 if any, else
    `theme-art: 14 images pixel-identical to themes/alttp (Chromium <version>)`.
  - **write** (`make theme-art-write`): renders the whole table twice,
    refuses (exit 1, nothing written) unless the two runs are byte-identical,
    then writes the PNGs into `themes/alttp/` and prints
    `theme-art: 14 images written to themes/alttp`. Unlike the goldens, art
    is regenerated whenever its mockups change: it is a build product of the
    mockups, committed so the app and the zip need no browser; its commit says
    which mockup changed.
- Both run the normaliser's and the Node script's self-tests first.
- The art is pinned, like the goldens, to the step-1 environment's
  Playwright 1.63.0 Chromium; another Chromium may give other pixels, which
  `make theme-art` reports as DIFFERENT with the version in its summary. It
  is outside the net and outside CI.

### Tuning passes

- A pass is: edit `theme.ini` (or, only when a sprite's own pixels are wrong,
  the generator's table and `make theme-art-write`), run `make
  theme-compare`, read the measures and the side-by-side images.
- **Frozen keys**: a pass never edits the keys that the page, the wrap width
  or the help length depend on: `list.top`, `list.bottom`,
  `list.row_height`, `list.label_x`, `list.right`, `list.font` and its
  font's `size`, `help.x`, `help.right`, `help.font` and its font's `size`.
  So page 12, width 48 and help 58 stay step 8's, and `git diff` of
  `theme.ini` from step 8's version to the last pass shows none of those
  keys (recorded). If a criterion can only be met by changing one, it is not
  changed in this step: the criterion gets that reason. (The plan's other
  branch, re-running step 9's check and updating step 11's bound, is
  therefore not taken; this keeps step 11's `UI_STR_HELP_LEN_MAX` (H-11-2)
  and its strings valid.)
- **No code change under `app/`** to meet a criterion: the look is theme
  data. A criterion that needs a renderer change gets that reason.
- **Free keys**: every y and x the frozen list leaves out (tab, title,
  message, help and footer baselines, `text_y` of list and notice rows,
  `notice.x`/`emphasis_x`, marker and sprite offsets, the title rule's `y`,
  `offset`, `dash`, `gap`, band rectangles, colours). Expected first finding,
  to be confirmed by the measures: the title rule's mockup `line` at y 77
  with stroke-width 4 covers y 75–79, while the renderer fills from `y`
  down, so `title.rule.y` likely becomes 75.
- **The help line keeps the message zone's place** (x 30, baseline 412), not
  00's x 34 and baseline 418: the plan keeps from the 16 px mockup only the
  help line's font, colour and zone ("under the list, in the message zone"),
  and the 12 px mockups put that zone at x 30, baseline 412. x 34 would also
  cut the help to 57 characters (a frozen key). Recorded as 00's reason.

### The criteria and their measures (`make theme-compare`, extended)

- `mockup_render.js` also writes, beside each rendered PNG, a tab-separated
  list of the mockup's `<text>` elements outside `defs`: bounding box
  (`getBBox`, user units = pixels), fill colour (computed, `rrggbb`), text.
  Its other behaviour, its self-proof and `make mockups`' output are
  unchanged (the extra file is ignored there).
- `theme_compare.py` gains an `offsets MOCKUP_PNG APP_BMP TEXTS` command:
  - a **text window** is a text's box grown by 4 px on each side; a pixel is
    **ink** of a colour when each channel is within 48 of it;
  - per text: the ink box of its colour inside its window, in the mockup and
    in the app; `dx`, `dy` = app minus mockup of the ink box's left and top,
    or `not found` when the app has no ink of that colour in the window;
  - `outside`: the count of pixels that differ between the two images and lie
    in no text window;
  - prints one line per text and a summary line.
- `theme_compare.sh` runs it after each `compare`, writes the per-text lines
  to `offsets.txt` beside `scores.txt`, and prints per mockup
  `theme-compare: <mockup>: outside <n> px, <k> texts, worst |dx| <a> |dy|
  <b>, <m> beyond 2 px, <z> not found`. Informational: it never changes the
  exit status, as the score does not.
- The three criteria of the plan, per mockup, measured:
  1. **Same zones** (frame, bands, sprites, rule): `outside` is 0.
  2. **Same text positions to a few pixels**: every found text has |dx| ≤ 2
     and |dy| ≤ 2.
  3. **Same colours**: no text is `not found` (and criterion 1 covers the
     non-text colours).
- 00 is judged on its frame, tabs, title and help line only: its list rows
  and footer are the 16 px variant, so its `outside` and its row texts fail
  by construction (README already says not to tune to it); those are its
  recorded reasons, and the help line's own offset (x 30 against 34,
  baseline 412 against 418) is a reason as decided above.
- **Stopping rule**: stop when every criterion holds on 01–08 and on 00's
  judged elements; otherwise stop after two consecutive passes that improve
  no figure (no mockup's `outside`, worst offset, beyond-2 or not-found count
  gets smaller), or after 10 passes. Every criterion still failing then gets
  a one-line reason (for example: SDL_ttf against Chromium glyph edges, a
  frozen key, a renderer change, 00 by construction).
- A pass may not trade one mockup against another silently: a pass that
  makes any mockup's figure worse is recorded as such.

## Testing Decisions

- Good tests drive the public interface: a planted image or SVG in, a PNG,
  a line or an exit status out; a theme folder in, a fault out. Nothing reads
  a module's internals.
- **Normaliser self-test** (`--self-test`, run by both art targets): planted
  RGB and RGBA PNGs with every filter type decode to the planted pixels; an
  opaque frame is written RGB and decodes back equal; a sprite with alpha 0
  and 255 is written RGBA with its transparent pixels as `0,0,0,0`; two
  encodes of the same pixels are byte-identical; refused with one line: a
  half-transparent pixel, an empty sprite, a non-opaque frame, a wrong size;
  check mode on planted folders gives exactly the expected `DIFFERENT`,
  `MISSING`, `EXTRA` lines and the summary when equal.
- **Node renderer self-proof** (like `mockup_render.js`'s planted SVGs): a
  planted mockup with an 8×4 red rect and a blue background: its line gives
  an 8×4 sprite of opaque red; with scale 0.5, 4×2; a selector matching
  nothing and one matching two elements are each refused with one line; a
  frame selector whose markup differs between two planted mockups is
  refused; a planted mockup requesting an `http:` URL is refused.
- **`theme_compare.py offsets` self-test** (in `--self-test`): planted
  images where a text's ink is moved by (1, −2) report dx 1, dy −2; ink of
  the wrong colour reports `not found`; a differing pixel inside a window is
  not counted in `outside`, one outside every window is; equal images give
  `outside 0` and every offset 0. The existing cases keep their expectations.
- **`test_theme` (in `make test`)**: a new case, alttp's folder holds only
  `theme.ini`, the files `theme_assets` lists for it, and `*-LICENSE.txt`
  files (a stray file would ship in the zip at step 13). Prior art:
  `test_alttp_fonts_are_data_copies` (directory walk) and
  `test_classic_assets`. `test_alttp_loads_within_the_app_ranges` is
  unchanged and must pass (page, width and help in range; with step 11, help
  equal to `UI_STR_HELP_LEN_MAX`, H-11-2).
- **`test_sdl_alttp` (in `make sdl-pc`)**: a new case, every sprite fits its
  zone with the loaded images' real sizes: each list sprite's offset plus
  height is within `row_height`; the right arrow ends inside the selected
  band; the scroll sprites end inside the selected band's right edge; each
  button sprite's `key_y` plus height is inside the footer band; the tab
  marker ends above `list.top`. `test_no_setting_row_is_cut` keeps passing
  with the 9 px arrow (it reads the sprite's width).
- No snapshot, golden BMP, golden state, mockup or `mockup_states.txt`
  changes; `classic` does not change.
- The side-by-side images, the scores and the measures are judged, not
  asserted: no threshold anywhere.

## Out of Scope

- Any change under `app/` or `rando/`; new theme keys; tinting or scaling
  sprites at run time.
- Changing a frozen key (page, width, help length); re-running step 9's
  check for a changed page or updating step 11's bound (not needed, since no
  frozen key changes).
- Editing the mockups' look; content edits to mockups (none needed).
- The 16 px variant of 00 (its rows, arrows and footer spacing).
- Shipping alttp as the default theme, the README's "where the theme lives"
  and the no-rebuild demonstration: step 13.
- Running the art targets in CI or in `make check`.

## Further Notes

- Why render in Chromium rather than draw the shapes in Python: the
  reference images of `make theme-compare` are Chromium renders, so art
  rasterised by the same Chromium matches them to the pixel (gradient
  stepping, the triforce's crisp edges at 1.25, the glyphs in the buttons);
  `outside 0` is then reachable, which makes criterion 1 exact.
- Why pixels and not bytes in the check: the bytes depend on the host's zlib
  as well as the pixels; the write mode's two-run byte identity covers
  determinism on the pinned host, the pixel check covers reproducibility.
- Why remove `[tabs.band]`: the same pixels from two sources would let a
  `theme.ini` colour edit and the frame disagree; the inventory puts the
  separator in `frame.png`.
- The asset count stays well inside `THEME_ASSETS_MAX` (32): one image,
  four fonts, thirteen sprites.
- Sprite colours are fixed in the image: the row cursor's yellow and the
  disabled cursor's `#bcc4ee` are two files, and the scroll and value arrows
  stay yellow whatever the row's colour, as in every mockup.
