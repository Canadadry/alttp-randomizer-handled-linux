## Problem Statement

Plan 3, Phase 3, step 4, verbatim from `docs/plan-3.md` (§3, Phase 3, item 4):

> 4. **Item pool and fill.** Port `itempool.py` and `randomizer.py`'s fill, with the RNG trace. Verified by `e2e` claims at the `fill` stage on every case (placement record and RNG trace equal to the golden's; the spoiler, which LADXR builds by reading the finished ROM back, is claimed later, in step 6), and by `make -C tests/ladx e2e` and `e2e-combos` printing no `DIVERGENT`. A `selftest` case proves a planted divergence prints `DIVERGENT`. This step wires LADX's `selftest`, `e2e` and `e2e-combos` into the root `make check`, verified by `make check` printing the LADX lines. This step also adds `make -C tests/ladx measure` for the run stopped after `fill`, with its Cortex-A7 projection in the step note (step 10 extends it to the whole pipeline).

Today the LADX library (`ladx/`) has CPython's RNG with a `words` counter (step 3.1), the settings table with `validate` and the short string (step 3.2), and LADXR's tier-1 logic graph and explorer (step 3.3). Step 3.3 left the world-setup randomisation to this step: `ladx_world_setup_defaults` is the only world setup C can make. Nothing in C draws a seed's world setup, builds LADXR's item pool, or places an item, and there is no LADX e2e driver: the 128 goldens' `run.txt` files (88 cases, 40 combos, each with `ws`, `pool`, `placer_pool`, `place` and `trace` sections) are checked by nothing on the C side. Every later step (tables, the nineteen seed-dependent groups, the assembly) needs a C run that reaches the same placement and the same RNG state as LADXR, and an e2e driver that later steps extend with write-log claims.

From the owner's point of view: an agent cannot play the game, so the only proof that a C seed is LADXR's seed is the golden. Until the fill matches byte for byte on every case, nothing after it can be claimed.

## Solution

The C library gains, in LADXR's statement order and with no allocation:

- a traced RNG: every draw through one of two generators (`rnd`, and the global `random` LADXR copies from it), each call reported as a structured record (generator, LADXR stage, method, arguments, result, MT words) to a caller-supplied sink;
- `WorldSetup.randomize` for tier 1 (bosses, minibosses, goal with the sign maze, multichest; the entrance part draws nothing in tier 1);
- `ItemPool` (with Python dict semantics) and `Randomizer.readItemPool`;
- `RandomItemPlacer` (`run`, `placeSpecificItem`, `__placeItem`, `logicStillValid`, `canStillPlaceItemPool`, `hasNewPlacesToExplore`);
- `ladx_randomize`, `Randomizer.__init__` up to the end of `item_placer.run`, with LADXR's outcome (ok, its `Error`, or the exception it would raise).

A host layer (`ladx/host/`) renders that run exactly as the oracle's `run.txt`, and a host generator `ladx_gen <case_dir> <out_dir>` writes it. A Python e2e driver (`tests/ladx/run_e2e.py`) runs `ladx_gen` on every case and combo and compares, per case, the golden's and C's **stage projection** of `run.txt` at the claimed stage (`init`, `ws`, `pool`, `fill`; this step ends at `fill` on every case). It prints `PASS`/`DIVERGENT` lines, proves itself on planted runs (`selftest`), and is wired into the root `make check`. A ROM-free fixture of LADXR's fill outcomes on refused seeds proves C refuses the same seeds the same way. `make -C tests/ladx measure` times the fill and projects it onto the Cortex-A7.

## Implementation Decisions

### Library (`ladx/`, pure C99, no allocation)

- **Traced RNG** (new public header, `ladx_rng`): a generator handle wrapping `LadxPyRandom` with its generator name (`rnd` or `global`) and an optional sink (a function pointer and a context). Every traced method takes the calling LADXR stage as an enum whose names are LADXR's `<module>:<qualname>` strings (`randomizer:Randomizer.__init__`, `worldSetup:WorldSetup.randomize`, `patches.maze:buildMaze`, `itempool:ItemPool.__randomizeRupees`, `randomizer:RandomItemPlacer.run`, `randomizer:RandomItemPlacer.placeSpecificItem`, `randomizer:RandomItemPlacer.__placeItem`; later steps add theirs). Methods this step needs: `seed`, `random`, `choice`, `choices` (integer weights), `shuffle`, `randint`, `getstate` and `setstate` (the last two as records only: the global generator is a struct copy of `rnd`, as `random.setstate(self.rnd.getstate())`). Each call emits exactly one record, the outermost call, as `TracingRandom` does: method, arguments (integers, the weights list, the seed bytes), result (an index, an integer, a double, or the permutation for `shuffle` and the picks for `choices`), and the MT words the call drew (the `words` counter's difference). `shuffle` shuffles an index permutation and applies it, so the record carries the permutation LADXR's trace prints. Capacity overflow (a permutation longer than the record's cap) is a broken run, never a silent truncation.
- **The library never formats a number into text.** Rendering, `float.hex` included, is the host's (below). Decided because `%a` differs from Python's `float.hex` and the device never needs the trace text.
- **World setup** (`ladx_logic.h`'s `LadxWorldSetup`, extended): adds `multichest` (an item), the sign maze (up to 22 signs as x, y and their directions, absent when the goal is not `maze`) and LADXR's constant tier-1 flags (`inside_to_outside`, `keep_two_way`, `one_on_one`, all true with `entranceshuffle=none`). New `ladx_world_setup_randomize(ws, validated, rnd)`: LADXR's `randomize` in statement order (boss `choice`s with the 3/6/shuffle removals and the `heartcontainers` rule, miniboss `choice`s over the mapping's values in key order, the goal branches: `maze` through `buildMaze`, `specific` with `randint` and `shuffle` of `"12345678"`, `a-b` ranges with `open` as -1, `instruments` with `goalcount=random`; then multichest's `choices`). `buildMaze` is ported with LADXR's `ALL_SIGN_OPTION_TILES` table (LADXR source data, MIT, not ROM bytes); its set is used only for membership, so no CPython set order is involved. `rnd.choice([])` returns LADXR's `IndexError` outcome ("Cannot choose from an empty sequence"), and 50 failed tries LADXR's `RuntimeError`. `goal=bingo*` (scope cut `goal-bingo`) returns unsupported.
- **`pickEntrances` in tier 1 draws nothing** and is not ported as code: the entrance pool is empty (`entranceshuffle=none`, `dungeonshuffle` and `randomstartlocation` unsupported), so `_randomizeEntrances` draws nothing and `inaccessibleEntrances` builds a Logic only to return an empty list. The world setup keeps the identity entrance mapping. Decided because a draw-free branch is proven by the trace equality; recorded so a tier-2 plan knows where to start.
- **Item pool** (new public header, `ladx_itempool`): an ordered item-count map with Python dict semantics, used for `ItemPool.__pool`, `readItemPool`'s dict and the placer's `_item_pool`: insertion order; `add` keeps a key at zero; `ItemPool.remove` deletes at exactly zero; a deleted key re-added goes to the end; negative counts kept (`readItemPool`'s forced items). Capacity is the item table's size. `ladx_itempool_build(pool, logic, validated, rnd)` ports `ItemPool.__init__` for tier 1 (the `overworld` branches other than `normal` are unreachable and not ported; `shopsanity` is unsupported), `__setup` in statement order and `__randomizeRupees` (with its re-draw loop, which never updates the weights). Its `RuntimeError`s ("Not enough seashells (<n>) available in itempool", "Wanted to remove more rupees from the pool then we have") are outcomes.
- **Randomizer and placer** (new public header, `ladx_randomizer`): one caller-owned struct holds the settings, both generators, the world setup, the logic (`ladx_logic_build` with the randomized world setup), the item pool as built, `readItemPool`'s result, the placer's pool and spot list, scratch explorers, and the outcome. `ladx_randomize(r, validated, seed, seed_len, sink)` runs `Randomizer.__init__` to the end of `RandomItemPlacer.run`: seed `rnd`, the `race` draw, world setup, the global copy, the logic, `readItemPool` (forced items, single-option spots, the `need_to_remove` loop), `addItem` for positive counts in dict order, `run`. The placer is a line-for-line port: `dungeon_keys` gathered by LADXR's name prefixes (`STONE_BEAK`, `KEY`, `NIGHTMARE_KEY`, compared on the item names, as Python's `startswith` does), shuffled; the bail counter; `placeSpecificItem` and `__placeItem` with their undo on `logicStillValid` failure (`spot.item = None` through `ladx_logic_place` with `LADX_ITEM_NONE`, which it already accepts; the item re-added at the end of the pool; the spot re-appended at the end of the list); `canStillPlaceItemPool` with Python's stable sorts (spots by `(0 if dungeon else option count, nameId)` with byte-wise name order, items by spot count from dict order) and its early return; `logicStillValid` with `accessibility=goal` testing windfish and otherwise the visited count against the location count. Outcomes: ok; LADXR's `Error` "Failed to place an item for a bunch of retries"; `AssertionError` with LADXR's message (`<a> != <b>`, "Sanity check failed: False", or empty for the bare in-loop assert); `IndexError` from an empty `choice`; `KeyError` (message `'<ITEM>'`) where `readItemPool` indexes a missing key. A capacity overflow or a logic failure is a separate broken status, never an outcome.
- **The `boomerang=default` with `accessibility=all` pair**: `ladx_randomize` does not check support (as `ladx_logic_build` builds the pair, step 3.3); it reproduces LADXR's `AssertionError` at `run`'s sanity check. Front ends (`ladx_gen` now, the app in Phase 4) call `ladx_settings_supported` first and refuse the pair.
- **Results for later steps**: after an ok run, the struct exposes the placement (through the logic's spots), the world setup, both generators' states and the pool as built, read through accessor functions; no later step re-runs the fill.

### Host layer (`ladx/host/`, C99, stdio allowed; built with `ladx/include` and itself on the include path)

- **Run text** (`ladx_run_text`): renders a run in the oracle's `run.txt` format exactly (`oracle_run.py`, `ladx_oracle.py`'s `ws_lines`, `pool_line`, `place_lines`, `Tracer.record`): `seed`, `settings` (the short string, `""` when empty), `ws` lines in WorldSetup attribute order (`entrance_mapping identity`, lists comma-joined, dicts `k=v`, `-` for None, booleans 1/0, the goal as its name or `=<digits>`, `sign_maze` as `x:y,...;d,...`), `words_before`, `pool`, `words_after`, `placer_pool`, `place <i> <class> <nameId> <item or ->`, `trace <n> <gen> <stage> <method> <args> -> <result> [<words>]` (integers in decimal, floats as CPython's `float.hex`: always 13 hex digits, `0x0.0p+0` for zero, sign kept), and `outcome ok | error <message> | crash <type> <message>` with `field`'s `""` for an empty message. It is a trace sink plus section writers; it writes the **fill projection** form (below), so the C file is its own projection.
- **`ladx_gen`** (`ladx/host/main/`): `ladx_gen <case_dir> <out_dir>` reads `config.txt` (through `ladx_settings_set`, then `validate`) and `seed` (32 lowercase hex digits), refuses unsupported settings (`ladx_settings_supported`; exit 2 naming the reason id), runs `ladx_randomize` with the run-text sink and writes `<out_dir>/run.txt`, exit 0 whatever LADXR's outcome (it is in the file); exit 2 on usage, a malformed input, an unsupported setting or a broken run; exit 1 on an I/O failure. `ladx_gen --time <case_dir>` prints only the run's elapsed microseconds (no file), for `measure`. Built `-O2` into `tests/ladx/build/ladx_gen`.

### Stage projection (one definition, Python; C writes it directly)

- Stages, in order: `init`, `ws`, `pool`, `fill`. Sections per stage: `init` = `seed`, `settings`; `ws` adds the `ws` lines; `pool` adds `words_before`, `pool`, `words_after`, `placer_pool`; `fill` adds the `place` lines.
- Trace lines per stage: the longest prefix of the trace whose stages are all in the stage's set: `init` {`randomizer:Randomizer.__init__`}; `ws` adds `worldSetup:WorldSetup.randomize`, `patches.maze:buildMaze`; `pool` adds `itempool:ItemPool.__randomizeRupees`; `fill` adds `randomizer:RandomItemPlacer.run`, `.placeSpecificItem`, `.__placeItem`. A golden with a line of the `fill` set after the `fill` prefix is malformed (exit 2).
- The `outcome` line is in the projection at stage S exactly when S's completion marker is absent (`init`: no `ws` line; `ws`: no `words_before`; `pool`: no `placer_pool`; `fill`: no `place` line): LADXR stopped inside S or before it. So an ok golden's `outcome ok`, which belongs to the whole run, is never claimed, and a fill error or a maze crash is.
- Everything else (`rom_sha1`, `spoiler_sha1`, the trace of `generateRom` and the spoiler) is outside every stage of this step.
- The projection is idempotent: the driver projects C's `run.txt` too, so a C run that goes further than ported never fails on what it adds.

### E2E driver (`tests/ladx/run_e2e.py`, `python3 -I -B`)

- Decided: Python, not ALttP's shell and awk, because step 5 and step 6 claim write-log projections that `write_log.py` already computes in Python; the driver imports it later instead of re-implementing it.
- Claims: `tests/ladx/claims.txt`, one `stage <name>` line that applies to every case of the directory run (cases and combos alike; no per-case lines, no `PENDING`, because every claim of plan 3 reaches every case). Comment lines `#`. Step 5 extends the grammar with its own line kind. An unknown stage, two `stage` lines or a malformed line exits 2.
- `run_e2e.py [--cases <dir>] [--claims <file>] [--gen <binary>] [<case>...]`: cases sorted by name (named cases only when given; an unknown name exits 2), each run as `<gen> <case_dir> <out_dir>` in a fresh temporary directory, in parallel; per case `PASS <case> (<stage>)`, or `DIVERGENT <case>` and indented detail lines: the first differing projection line as `<section>: line <n>:` then `golden: <line>` and `c: <line>` (`<end>` past the end), or `c generator exited <code>` with its stderr's first lines, or `c wrote no run.txt`; then `e2e: <p> pass, <d> divergent`; exit 0, 1 when one is divergent, 2 on a usage, claims or golden-format error. A missing generator makes every case `DIVERGENT` with `no C generator: <path>` (as ALttP's driver).
- `run_e2e.py --self-test`: a planted case tree (copies of one real golden's `run.txt` and `config.txt`) and fake generators (small Python scripts writing a planted `run.txt`). Expected: identical → `PASS`; a changed `place` line, a changed fill-stage trace line, a C trace one line short, one extra C fill-stage trace line, a changed `ws` line, a non-zero exit, no `run.txt` → `DIVERGENT`; a changed `generateRom` trace line, a changed `rom_sha1` or `spoiler_sha1` → `PASS`; a claim at `ws` with a changed `place` line → `PASS`; a golden with `outcome error` and no `place` against a C `outcome ok` with places → `DIVERGENT`; a golden with a fill-stage line after a `generateRom` line → exit 2. Prints `e2e: self-test, <n> planted runs as expected`, else one `e2e: self-test failed: <case>` line each, exit 1.
- `tests/ladx/Makefile`: `selftest` (the self-test), `e2e` (`cases/`), `e2e-combos` (prints `e2e-combos: the combination cases`, then `combos/`), both building `ladx_gen` first and taking `CASES="<case> ..."`. Root `Makefile`: `selftest`, `e2e` and `e2e-combos` run ALttP's then LADX's target; `make check` unchanged otherwise. `help` lines in both.

### Fill-outcome fixture (ROM-free, oracle side)

- Decided (owner decision taken here): the case seeds are all `outcome ok` by construction (`ladx_cases.py pick`), so they cannot prove C refuses what LADXR refuses. A new committed fixture `tests/ladx/oracle/fill_outcomes.txt` records LADXR's fill projection on seeds that are not case seeds, from the same derivation: for every case and combo, every candidate `derive(name, k)` below its chosen `k` (refused by `pick` for the Nintendo-bytes check or by outcome: fill errors, the maze crash); the refused single `boomerang-default`'s candidates `k = 0..7`; and the tier-1 lines of `determinism_cases.txt` (`pain`'s fill error among them; `bingo` left out, cut). One line per run: `<label> <k or -> <seed hex> <ok|error|crash> <lines> <digest> [<k=v> ...]`, `<digest>` the first 16 bytes, in hex, of SHA-512 of the run's `fill` projection text (lines joined by `\n`, final newline), `<lines>` its line count; a `#` header documents the format. Seeds, settings and digests only: no ROM byte.
- Generator: `tests/ladx/oracle/gen_fill_outcomes.py` (`oracle_run.py`'s driver in `SKIP_ROM_GENERATION` mode, no ROM, the LADXR checkout at the pin, `PYTHONHASHSEED=0`), writing the file; `--check` regenerates into `tmp/` with `PYTHONHASHSEED=1` on the setup checkout and prints `DIFFERENT`/`MISSING` or `fill-outcomes: <n> runs byte-identical to tests/ladx/oracle/fill_outcomes.txt`. Decided: no fresh-clone second run, because the fill's independence from hash seed and checkout is already proven by `determinism.sh` (step 1.8, and `--full --all` in step 2.5) on the same code path. Outside the net, like the other generators; `nintendo_bytes.py` on the file reports `0 literal runs` (step note).
- C side: `test_fill --fixtures` (in `LOGIC_TESTS`, so `make logic` and `make unit-arm`) replays every line through `ladx_randomize` and the run-text renderer and compares line count, digest (`ladx_sha512`) and outcome kind, naming the first mismatching label.

### Measure

The step note records the figures. Exit 0 whatever the figures, 1 when a measurement cannot be taken.

## Implementation Chunks

Claim: `test_rng` (each traced method draws exactly what `ladx_pyrandom` draws, its `words` equal to the counter's difference, one record per call, the permutation applied as LADXR's `x[to] = before[perm[to]]`) and `test_run_text` (records built by hand render byte-identical to real golden lines: the race case's `random ... -> 0x1.1d12acb9114b1p-1 [2]`, a `choices 12 20,20,...` line, a `shuffle` line, the `seed` line; `float.hex` of 0.5, 0.0, -0.0, the smallest subnormal and 1 - 2^-53 against CPython's strings), under `make test`; `make -C tests/ladx lint` builds `ladx/host/`; `make unit-arm` builds and runs them.

## Testing Decisions

- A good test drives the public interface (`ladx_rng`, `ladx_world_setup_randomize`, `ladx_itempool`, `ladx_randomize`, the run-text renderer, `ladx_gen`, the driver's CLI) and compares with LADXR's own output (goldens, `item_pools.txt`, `fill_outcomes.txt`, strings CPython printed), never with the C code's internals. Each new test is mutation-checked by hand once (a flipped tie-break, a removed re-append, an off-by-one bail counter must each fail a test), as steps 3.1 to 3.3 did.
- The e2e claim is the primary evidence: every case and combo's fill projection equal to the golden's. It is not weakened: no stage is lowered for a failing case, no golden is edited; a divergence proven to come from a Phase 2 artifact is fixed at the oracle (§2).
- Modules tested: `test_rng`, `test_run_text`, `test_world_setup`, `test_itempool` (fixture replay under `--fixtures`), `test_fill` (fixture replay under `--fixtures`), each in `tests/ladx/Makefile`'s `UNIT_TESTS`, failing through `unit/support.h`'s `test_fail`; the three fixture replays in `LOGIC_TESTS`. Tests that need the host renderer link the host layer's objects; `unit-arm` compiles `ladx/host/` sources too.
- The driver is tested by its own `--self-test` on planted trees and fake generators (run by `make selftest`), as ALttP's `selftest.sh` and `rom_check.py`'s self-test do.
- Prior art: `tests/ladx/unit/test_logic.c` (`--fixtures` replay of oracle fixtures), `test_pyrandom.c` (vectors CPython printed), `tests/alttp/run_e2e.sh` and `selftest.sh` (claims, `PASS`/`DIVERGENT`/summary lines, planted divergence), `tests/ladx/oracle/rom_check.py` (Python self-test on planted runs), `tests/alttp/measure.sh` (Cortex-A7 factors).
- `make test` stays about as fast as today: the fixture replays and the e2e runs are in `make logic` and `make check`, not `make test`; the step note records `make test`'s time.

## Out of Scope

- `generateRom` and everything after the fill: tables (step 5), every seed-dependent write group and the spoiler (step 6), the assembly and `ladx_patch` (step 7), `rom-check` with a C generator.
- `ForwardItemPlacer` (`forwardfactor` fixed at 0.0), plandomizer plans, entrance shuffle and every `overworld` other than `normal` (their `pickEntrances`, `dungeonchain`, `mapgen` and pool branches), `shopsanity`, and `goal=bingo*` (scope cut `goal-bingo`).
- LADXR's retry with a new seed after a fill error: that is `main.py`'s and the app's (Phase 4) concern; C reports the outcome.
- The LADX-aware debugging skills (step 8) and the whole-pipeline measure (step 10).
- Write-log claims and their driver extension (step 5).

## Further Notes

- The trace's stage names are LADXR's `co_qualname`s, private names unmangled (`RandomItemPlacer.__placeItem`), as the goldens show.
- Every golden's `outcome` is `ok`, so under the projection rule no case's outcome line is claimed by this step; the fixture of chunk 6 is what claims error and crash outcomes.
- `canStillPlaceItemPool`'s `set(spot.getOptions())` is used only for membership; `get_options_from` in `buildMaze` reads its set only for membership too, so no CPython set or hash order enters the port.
- The `words` counter starts at 0 when seeded, like `TracingRandom._words`; `words_before` and `words_after` are `rnd`'s counter, and the global copy carries the counter but its trace records only per-call differences.
- Golden runs are up to about 1,030 lines; the fill projection is at most about 700 of them, so the driver's comparison is cheap; the run time is the fill itself.
- If a C capacity (pool entries, spot list, permutation length) proves too small on a case, it is raised with the measured maximum in the step note, as step 3.3 did for the logic.
