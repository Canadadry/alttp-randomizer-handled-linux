# check-e2e

`make -C tests/rando test` is the dev loop: unit tests, seconds. `make -C tests/rando e2e` is every case of `tests/rando/cases/` generated by the C port and diffed against what the VT oracle wrote: the RNG trace, `attempts`, `spoiler.json` and, for a claim `<case> all <group>`, the ROM write log `rom_writes.txt` up to the last write of that group (`tests/rando/write_groups.txt` names the groups, in `writeToRom`'s order). `make -C tests/rando e2e-combos` does the same for `tests/rando/combos/` with `tests/rando/combo_claims.txt`.

In this repository `e2e` is part of `make check`, which `check-net` runs after each PRD and after each `skill:` step: per-PRD checking is `check-net`'s job, not this skill's. This skill is run only by plan-pilot, for a `skill: check-e2e` step of the plan, as a dedicated pass over the whole case list.

A red case is always a bug in the C port. Never run `tests/rando/oracle/gen_golden.sh`, never edit a file of `tests/rando/cases/` or `tests/rando/combos/` to get green.

Every e2e bug leaves behind a unit test that catches it in `make -C tests/rando test`. That is the point: the next time, the dev loop catches it in seconds instead of the net catching it later.

## Rule #1 — never wait on the human

No one answers during this loop. A `QUESTION:` from any sub-agent goes to a fresh `guideline` agent, never to the user. The only way back to the human is the stop after 3 failed attempts (step 5).

## Rule #2 — you are the human at fix-bug's commit gate

`fix-bug` stops once, at its `git-commit` proposal, for a human go-ahead. Here, you give or refuse it, after running the checks of step 4 yourself. Never accept on the strength of an agent's report.

## Loop

### 1. Run the net
Run `make -C tests/rando e2e` and `make -C tests/rando e2e-combos`. Both green → report `E2E-GREEN:` with the list of `fix:` commits made during this run, and stop.

### 2. Split the red into failures
One failure = one `DIVERGENT <case>` line, from either run, with the detail lines under it. Keep the full output of each, and which run (`e2e` or `e2e-combos`) it came from.

Rank them all in one pool and take the first; it is the cheapest to diagnose:

1. `baseline`, if red.
2. A **seed-level failure**: any detail that is not a `rom_writes.txt:` line or `c wrote no rom_writes.txt` (the trace, `attempts`, `spoiler.json`, a stage check, the generator's exit status). Earliest differing draw first (attempt, then draw number, from the trace diff). A write is never debugged while its seed already differs.
3. A **write-log failure** (`rom_writes.txt: <group>: first differing write <n>:`, `rom_writes.txt: c ends after <k> writes, claim needs <N>`, `c wrote no rom_writes.txt`, `rom_writes.txt: line endings differ`): the earliest group in `write_groups.txt` order first, then the lowest write number. A short or missing log ranks at the group of its first missing write: the golden's write `k + 1` (write 1 for a missing log), grouped by the golden line's tag.
4. On a tie: `e2e` before `e2e-combos`, then case order.

Handle it alone; the others wait for the next run, since a fix often repairs more than one.

### 3. Invoke fix-bug on it
Invoke the `fix-bug` skill in place. Its argument is a bug report you write, containing:

- **Symptom**, verbatim: the `make -C tests/rando e2e` (or `e2e-combos`) output for this failure, nothing paraphrased.
- **Reproduction**: the command that replays the case alone: `tests/rando/run_e2e.sh <case>` for `cases/`, `RANDO_CASES=tests/rando/combos RANDO_CLAIMS=tests/rando/combo_claims.txt tests/rando/run_e2e.sh <case>` for `combos/`. Then:
  - a seed-level failure: the diff of the case's VT trace against the C trace, starting at the first draw that differs;
  - a write-log failure: the first differing `rom_writes.txt` line, golden and C, verbatim from the detail (`<address> <bytes> <Rom method>`, `<end>` when absent), with its group and write number; for a short or missing log, the golden's first missing line (`sed -n '<k+1>p'` of the golden's `rom_writes.txt`). The address is a PC offset, the method is the VT setter that wrote it.

  The case's `config.json` says which option it exercises.
- **Constraints on the fix**, to be carried into every stage:
  - The RED test is a **unit test run by `make -C tests/rando test`**, registered in `tests/rando/Makefile`'s `UNIT_TESTS`. Never a new case in `tests/rando/cases/` or `tests/rando/combos/`.
  - For a write-log failure, the RED test is a `test_rom_*` unit test: a hand-built world passed to `rando_rom_write` through a recording writer, checking the writes it records. Never a whole golden `rom_writes.txt` read back.
  - Its cost is **negligible**: it builds the minimal world state that reaches the cause, it does not run a whole generation, and it runs well under 50 ms. Needing a full seed to go red is the sign the real cause has not been found — go back to diagnosis, don't ship it.
  - The fix turns the new test, `make -C tests/rando e2e` and `make -C tests/rando e2e-combos` green.
  - A divergence is a bug. Never regenerate or edit a golden.
- **Already eliminated**, on a retry (step 5): every hypothesis the previous attempts disproved, and why their commit was refused.

### 4. The commit gate — check, then accept or refuse
When `fix-bug` proposes its commit, check each point yourself, with commands you run:

1. The diff adds (or extends) a test under `tests/rando/unit/`, and its binary is in `UNIT_TESTS`.
2. That test reads no file of `tests/rando/cases/` or `tests/rando/combos/` and runs under 50 ms (time it).
3. It **fails on the pre-fix code**: in a throwaway `git worktree` of `HEAD` under `tmp/`, apply only the diff's `tests/` changes, build and run the test — it must fail. Then it passes on the working tree.
4. `make -C tests/rando test`, `make -C tests/rando e2e` and `make -C tests/rando e2e-combos` are green, and the failure you handed over no longer appears.

All four hold → accept: `fix-bug` commits (folded into `HEAD` when `progress.md` exists, see `git-commit`). Remove the worktree.
Any one fails → refuse, with the reason. Nothing is committed; restore the working tree to `HEAD` before the next attempt.

### 5. Count the attempt
An attempt fails when you refuse the commit, or when `fix-bug` stops on its own (cause unproven after two debug agents, verification failing twice).

- Fewer than 3 failed attempts on this failure → back to step 3 with the same failure, the bug report extended with what was eliminated and why the last attempt failed.
- 3 failed attempts → stop. Report `E2E-FAILED:` to the user: the failure, the three attempts, what each eliminated, and which observation is missing. This is the only moment this skill hands back to the human.

### 6. Loop
After an accepted commit, back to step 1: `e2e` and `e2e-combos` from the top.

## Output

- `E2E-GREEN:` + the `fix:` commits made, or folded into `HEAD` (possibly none).
- `E2E-FAILED:` + the report of step 5. The working tree is back at `HEAD`, nothing half-fixed is left behind.

Never push: the caller decides.
